release gate reports, the evidence behind it, and the exact sequence the owner

[Accepted Release Warnings](ACCEPTED-RELEASE-WARNINGS.md) page and the owner
pre-tag checklist; it does not replace the full audits, which live in the
`research/` records (`research/50`–`research/57`) as repository files.

## Executable manifest drift check

`scripts/check_release_manifest.py` verifies that this manifest and the actual
repository state still agree. It is **read-only** and deterministic: it never
modifies a file, the version, the release gate or the Git state.

```
python scripts/check_release_manifest.py
python scripts/check_release_manifest.py --gate-report <release_check-report.json>
```

It compares the manifest with:

- the **version** (`pyproject.toml`, and the manifest's stated version);
- the **release gate** — classification `READY WITH WARNINGS`, `blockers: []`,
  and the accepted set `{W7, W12}` (reusing the warning-drift comparison so the
  policy, this documentation and the actual gate are cross-checked together);
- the **release validation** — the pytest, labs, MkDocs, licensing and version
  gate results, plus a successful Ruff and mypy run;
- the **CI structure** — exactly five jobs, `release-readiness` present, one
  release-gate invocation, a drift step that consumes the captured report, and
  no `continue-on-error`;
- the **tag state** — `v0.0.1` present and `v0.1.0` absent;
- the **protected invariants** the manifest names.

It reports **every** detected discrepancy rather than stopping at the first. A
non-zero exit means the manifest must be reviewed and corrected — the release
state is not modified by the check. `--gate-report` consumes an already-captured
`release_check.py --json` report instead of running the gate, matching the
single-execution CI design.

This check **complements** `scripts/check_warning_drift.py`: the drift check
covers the accepted-warning surfaces, while this one covers the whole manifest
against the release state. This manifest is **evidence and documentation, not an
authority**: it can never override the actual release gate, and the gate's
result is always the source of truth.

## Executable owner pre-tag validation

`scripts/pre_tag_check.py` runs the owner release sequence (section 7) as one
executable, read-only command. It orchestrates the established checks — version,
licensing, tests, labs, Ruff, mypy, MkDocs, the release gate, the warning drift
check, the manifest drift check and the Git/tag invariant — capturing the release
gate once and reusing its report in both drift checks. It is fully documented on
the [Accepted Release Warnings](ACCEPTED-RELEASE-WARNINGS.md) page; this manifest
only references it, and the owner release sequence above remains prose and is not
duplicated. The command is read-only and never commits, pushes, tags or
publishes; a successful run means the repository is ready for owner review, not
that the release is authorized or performed.

To capture the owner-review evidence in machine-readable form, run:

```
python scripts/pre_tag_check.py --json
```

It prints a single deterministic JSON report (with the same exit code as the
human-readable mode) that records the result, the target version, the release
gate's classification, blockers and warning set, and the twelve checks — suitable
for archiving in the release record. The full schema and semantics are documented
on the [Accepted Release Warnings](ACCEPTED-RELEASE-WARNINGS.md) page.

The report also carries a **SHA-256 attestation** binding it to the exact
repository state that produced it. Re-check an archived report (read-only, without
re-running any check) with:

```
python scripts/pre_tag_check.py --verify-report <report.json>
```

This is integrity evidence, not a digital signature; it detects a modified report
or a changed tree but makes no claim about authorship or provenance. Archive the
report **outside** the repository so the report file itself does not change the
repository-state digest. See the
[Accepted Release Warnings](ACCEPTED-RELEASE-WARNINGS.md) page for the full
design.

An **optional** owner signature can add provenance on top of that integrity
evidence, without a key being required for normal validation. Sign a reviewed
report with the local OpenSSL 3.x (Ed25519) tool, and verify it with the
corresponding public key:

```
python scripts/pre_tag_check.py --sign-report <report.json> --private-key <private.pem> --output <report.signed.json>
python scripts/pre_tag_check.py --verify-report <report.signed.json> --public-key <public.pem>
```

The private key stays under owner control; only the public key and its `key_id`
fingerprint belong in archived evidence. Signing is optional and neither
authorizes a release nor creates, pushes or modifies a Git tag, and an unsigned
report still verifies for its SHA-256 integrity. The full design is on the
[Accepted Release Warnings](ACCEPTED-RELEASE-WARNINGS.md) page.
